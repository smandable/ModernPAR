# Verification of high-risk architectural decisions

## Claim 1 — verdict: **nuanced**

**Claim:** par2cmdline-turbo (animetosho) is the best PAR2 engine to integrate into ModernPAR, and its GPLv2 license is compatible with shipping a closed-or-open native mac app outside the Mac App Store. Sub-claims: license is GPLv2; current maintenance status; build system is CMake; C++ standard; whether it can be compiled/linked into a macOS app or must be a separate process for GPL/sandbox reasons.

**Evidence:**
- LICENSE/COPYING (primary): COPYING on the `turbo` branch begins 'GNU GENERAL PUBLIC LICENSE / Version 2, June 1991'. Source header src/par2cmdline.cpp states '...under the terms of the GNU General Public License as published by the Free Software Foundation; either version 2 of the License, or (at your option) any later version.' So the precise license is GPL-2.0-OR-LATER, not bare GPLv2. configure.ac repeats the same 'or (at your option) any later version' grant. GitHub API normalizes the SPDX id to GPL-2.0 / 'GNU General Public License v2.0', which loses the '+/-or-later' distinction. The claim's 'GPLv2' is therefore imprecise (the doc-03 label 'GPL-2.0-or-later' is the accurate one).
- BUILD SYSTEM (claim is REFUTED): The repo does NOT use CMake. Recursive tree of the `turbo` branch (api.github.com .../git/trees/turbo?recursive=1, truncated:false) contains NO CMakeLists.txt or any *.cmake file anywhere. The Unix/macOS build is GNU autotools: root contains automake.sh, configure.ac, Makefile.am, config.guess, config.sub, m4/, depcomp, mkinstalldirs. Windows build is MSVC project files: par2cmdline.sln, par2cmdline.vcxproj, libpar2.vcxproj. README says 'See original README for build instructions' (the upstream par2cmdline autotools flow: ./automake.sh && ./configure && make).
- C++ STANDARD: README states 'ParPar backend requires C++11 support', and notes turbo 'replac[es] [OpenMP] with C++11's threads' enabling fully static builds. However the actual build floor is HIGHER: configure.ac has a 'C++14 check' invoking AX_CXX_COMPILE_STDCXX(14, noext, mandatory). So: C++14 mandatory at configure time; C++11 minimum for the ParPar backend code. It is NOT C++17. Doc 03's 'C++11' label is a slight understatement of the build's C++14 requirement.
- MAINTENANCE (ACTIVE - confirmed): GitHub API repo metadata: archived=false, disabled=false, default_branch='turbo' (note: NOT 'master' - this is why naive raw.githubusercontent.com/.../master/ fetches 404), pushed_at=2026-02-28, updated_at=2026-06-07, open_issues=6, stars=184. Latest release v1.4.0 published 2026-02-09. Forked version string X_VERSION '1.4.0' (atop upstream par2cmdline 1.1.1 base in AC_INIT).
- macOS arm64 SUPPORT (confirmed): v1.4.0 release assets include par2cmdline-turbo-1.4.0-macos-arm64.zip AND par2cmdline-turbo-1.4.0-macos-universal.zip (plus macos-amd64, linux arm64/amd64/armhf, freebsd aarch64/amd64, win-arm64/x64). Prebuilt native arm64 + universal binaries exist, so a bundled-CLI approach needs no compilation.
- GPL LINKING LAW (FSF primary source, gnu.org/licenses/gpl-faq.html): 'Linking a GPL covered work statically or dynamically with other modules is making a combined work based on the GPL covered work. Thus, the terms and conditions of the GNU General Public License cover the whole combination.' This means compiling/linking turbo into ModernPAR's binary (the doc-04 plan: 'Compile par2cmdline-turbo as a C++ SwiftPM target via Swift/C++ interop') makes the entire ModernPAR binary GPL-covered -> a CLOSED-source ModernPAR linking turbo this way would be a GPL violation. Only an open-source (GPL-compatible) ModernPAR may link it.
- SEPARATE-PROCESS BOUNDARY (FSF primary source): 'pipes, sockets and command-line arguments are communication mechanisms normally used between two separate programs. So when they are used for communication, the modules normally are separate programs.' vs '...included in the same executable file, they are definitely combined in one program. If modules are designed to run linked together in a shared address space, that almost surely means combining them into one program.' This validates doc-03's recommendation: shipping turbo as a bundled CLI helper invoked via Foundation.Process keeps the GPL at arm's length, allowing a closed-source UI. Doc 04's in-process linking does NOT.
- APP STORE INCOMPATIBILITY (confirmed, matches the 'outside the Mac App Store' part of the claim): The VLC/Apple precedent (computerworld.com 'GPLv2 blocks VLC from Apple's App Store'; videolan.org LGPL relicensing press release; lwn.net 525718) establishes that Apple's App Store terms impose 'further restrictions' (usage rules, DRM) that conflict with GPLv2 Section 6; VLC was pulled in 2010-2011 and relicensed libVLC to LGPL specifically to ship on Apple stores. So distributing GPL-licensed turbo via Developer-ID/notarized OUTSIDE the Mac App Store avoids this conflict - the claim is correct on this narrow point.
- 'BEST ENGINE' SUB-CLAIM (subjective, doc-supported but conditional): doc 03's engine comparison table rates turbo as 'fastest full engine' (par2cmdline core + ParPar SIMD GF16/MD5/CRC, C++11 threads, no OpenMP, prebuilt arm64+universal, active). Alternatives: official par2cmdline (also GPL-2.0, needs LLVM/OpenMP, slower), libpar2 (same GPL repo, no clean public API), ParPar (CC0 but create-only), gopar (BSD-3 but hobby/unproven). 'Best' holds among full create/verify/repair engines IF GPL is acceptable; for a permissive-license requirement none of the GPL options qualify.

**Recommendation:** Treat the claim as directionally right but materially imprecise on two points; do NOT adopt it verbatim. (1) Correct the license label everywhere to 'GPL-2.0-OR-LATER' (COPYING says GPLv2 but every source header and configure.ac grant '(at your option) any later version'). 'GPLv2' alone understates the rights. (2) FIX the build-system assumption: par2cmdline-turbo is autotools (+ MSVC project files), NOT CMake - any ModernPAR build integration plan that assumes a CMakeLists.txt is wrong. Options: (a) consume the prebuilt macos-arm64/universal binary from the v1.4.0 release, or (b) build from source via ./automake.sh && ./configure && make (requires a C++14-capable compiler per configure.ac, not merely C++11), or (c) write your own CMake/SwiftPM wrapper around src/. (3) RESOLVE the internal contradiction between doc 03 and doc 04 before committing architecture: per the FSF, in-process static/dynamic linking (doc 04's Swift/C++ interop SwiftPM target) makes the whole ModernPAR binary GPL - acceptable ONLY if ModernPAR is itself GPL/open-source. If ModernPAR is to remain closed-source, you MUST use the doc-03 separate-process pattern (bundle the turbo CLI, drive it via Foundation.Process over command-line args/pipes) to keep the GPL at arm's length. The claim's phrase 'closed-or-open' glosses over this: closed + linked = GPL violation; closed + subprocess = OK; open = either is fine. (4) The 'outside the Mac App Store' qualifier is essential and correct - GPLv2 is incompatible with App Store distribution terms (VLC precedent); keep distribution to Developer-ID/notarized direct download. (5) Get a real legal review before release; 'not legal advice' caveat in doc 03 stands.

## Claim 2 — verdict: **confirmed**

**Claim:** RAR extraction can be shipped legally and natively on arm64 macOS: the RARLAB UnRAR license permits extraction-only bundling (forbidding only re-creation of RAR compression / a RAR-compatible archiver), while macOS's bundled libarchive cannot fully cover RAR (notably password-protected and multi-volume).

**Evidence:**
- UnRAR source license (canonical, verified via ScanCode LicenseDB https://scancode-licensedb.aboutcode.org/unrar.html and 7-zip.org/license.txt and the aawc/unrar mirror) states verbatim: the UnRAR source code 'may be used in any software to handle RAR archives without limitations free of charge, but cannot be used to develop RAR (WinRAR) compatible archiver and to re-create RAR compression algorithm, which is proprietary.' This explicitly PERMITS extraction-only bundling (including in commercial/closed apps) and FORBIDS only (a) re-creating RAR compression and (b) building a RAR-compatible *archiver* (i.e. creating .rar files).
- Attribution is mandatory: 'Distribution of modified UnRAR source code in separate form or as a part of other software is permitted, provided that full text of this paragraph ... is included in license, or in documentation if license is not available, and in source code comments.' So ModernPAR must ship the UnRAR license notice and keep the source comments.
- Warranty/liability: license is AS-IS — 'THE RAR ARCHIVER AND THE UnRAR UTILITY ARE DISTRIBUTED "AS IS". NO WARRANTY OF ANY KIND IS EXPRESS OR IMPLIED. YOU USE AT YOUR OWN RISK.' No royalty, no copyleft; ScanCode classifies it as source-available / proprietary-free for the specified uses (non-OSI, but no barrier to a proprietary macOS app).
- The RAR/WinRAR EULA section 19 (rarlab.com/license.htm) independently reinforces the only hard prohibition: 'Neither RAR binary code, WinRAR binary code, UnRAR source or UnRAR binary code may be used or reverse engineered to re-create the RAR compression algorithm, which is proprietary, without written permission.' Extraction is not restricted.
- CORRECTION to doc 05: the current UnRAR source version is 7.2.4 (unrarsrc-7.2.4.tar.gz on rarlab.com/rar_add.htm), NOT '7.13 as of Sep 2025' as doc 05 §1 states. The '7.13' figure conflates the WinRAR/RAR app version line with the UnRAR source tarball version. This is a factual error in the doc but does not change the conclusion.
- libarchive RAR support is read-only and incomplete. The official libarchive wiki LibarchiveFormats page lists 'rar (read only, original and RAR v5 format)' — it reads RAR3/4 and RAR5 but the page documents no encryption or multi-volume support.
- DECISIVE technical limit — verified directly in libarchive's RAR5 reader source (archive_read_support_format_rar5.c on master): on a HEAD_CRYPT block it sets is_data_encrypted/has_encrypted_entries then calls archive_set_error(..., ARCHIVE_ERRNO_FILE_FORMAT, "Encryption is not supported") and returns ARCHIVE_FATAL. Password-protected RAR is therefore NOT extractable via libarchive. The rar4 reader likewise has no password support.
- libarchive RAR5 reader also explicitly does NOT process recovery data: source comment 'An offset to additional Recovery data. This is not supported by this unpacker. Recovery data are additional Reed-Solomon codes...' — so Reed-Solomon recovery records are ignored.
- Real-world precedent that the extraction-only UnRAR bundling pattern is App-Store-legal: Keka (apps.apple.com/us/app/keka/id470158793) ships on the Mac App Store and via Developer ID and bundles RARLAB UnRAR, crediting it in release notes ('Updated UNRAR ... Thanks to rarlab', recently to UNRAR 7.10). Confirms link-the-library + attribution is an accepted shipping pattern.
- MacPAR deLuxe ground truth (docs/research/00-source-notes.md) confirms ModernPAR only ever EXTRACTS RAR (libUnrar.dylib; RAR 2.x/3.x/5.x, multi-volume, SFX, password) and never CREATES .rar — so the UnRAR field-of-use restriction (no RAR-compatible archiver) does not bind ModernPAR at all.

**Recommendation:** Ship two engines, exactly as doc 05 recommends: (1) RAR -> build RARLAB UnRAR from the official source tarball (unrarsrc, currently 7.2.4) as a static lib/XCFramework, linked into the app (do NOT spawn the CLI binary, which causes sandbox/codesign friction). This is the only backend that reliably covers RAR2/RAR3/RAR5 + multi-volume + SFX + password (prompt-once via the UCM_NEEDPASSWORDW / UCM_CHANGEVOLUMEW callbacks). (2) zip (and optional 7z read) -> macOS libarchive (BSD-2-Clause), linked via the SDK libarchive.2.tbd stub. Compliance to-dos: bundle the UnRAR license.txt verbatim in the app's acknowledgements/About and keep the upstream source comments (the license's only obligation). RAR capabilities that MUST be dropped: (a) CREATING .rar archives — legally forbidden and never a MacPAR feature anyway; (b) do NOT route RAR through libarchive/XADMaster/p7zip for the password or RAR5 path — libarchive provably returns 'Encryption is not supported' (ARCHIVE_FATAL) on encrypted RAR and ignores Reed-Solomon recovery, and the LGPL relink obligation makes XADMaster unattractive for a closed app. Caveat: if ModernPAR must be strictly OSI-open-source with zero non-free deps, UnRAR (non-OSI, field-of-use restricted) becomes a conflict point — then ship it as an optional/separate component or fall back to LGPL XADMaster (dynamically linked) at the cost of RAR5/password fidelity. Also fix the factual error in docs/research/05 §1: UnRAR source is 7.2.4, not 7.13.

## Claim 3 — verdict: **nuanced**

**Claim:** SwiftUI is sufficient to build ModernPAR's UI (multi-window document-like sets, file-list table with per-row status, live progress, drag-drop, dock-drop, menu commands, Settings) on macOS 26 with little/no AppKit bridging.

**Evidence:**
- Multi-window 'document feel' is genuinely native: WindowGroup(for:) + openWindow(value:) creates one scene per Hashable+Codable value, reuses an existing window for an equal value, and Codable conformance gives SwiftUI built-in window state restoration (Apple WWDC22 'Bring multiple windows to your SwiftUI app' https://developer.apple.com/videos/play/wwdc2022/10061/ ; WindowGroup docs https://developer.apple.com/documentation/swiftui/windowgroup ). The doc's SessionRoute(Codable,Hashable) design (04 §2.3) is sound.
- Menus/shortcuts/Settings are fully native: the Settings { } scene auto-creates the Cmd-, 'Settings…' item and its window; CommandGroup/CommandMenu insert/replace menu-bar items; .keyboardShortcut wires accelerators incl. Cmd-. (Apple 'Menus and commands' https://developer.apple.com/documentation/swiftui/menus-and-commands ; SerialCoder 'Presenting the Preferences Window…'; Swift with Majid 'Commands in SwiftUI'). No AppKit needed here.
- Multi-column file list with per-row status is native: SwiftUI Table (macOS 12+) supports TableColumn closures rendering Image/custom views per row, single/multi selection via id bindings, and column sorting via KeyPathComparator/sortOrder (Apple TableColumn docs https://developer.apple.com/documentation/swiftui/tablecolumn ; useyourloaf 'SwiftUI Tables Quick Guide'). Live per-row updates work with @Observable as the doc (04 §6) describes.
- REFUTES the doc's NSOpenPanel rationale: folder selection does NOT require NSOpenPanel/canChooseDirectories. fileImporter(isPresented:allowedContentTypes:[.folder]) selects directories on macOS (Apple Forums 749733: 'Your code works as I'd expect on macOS'; Apple fileImporter docs). The doc (04 §7.1) overstates this as an AppKit bridge point.
- REAL AppKit-adjacent limitation #1 (drag-drop sandbox): Apple DTS engineer Quinn confirms SwiftUI's dropDestination(for: URL.self) does NOT 'auto-start' security scope the way file panels do — url.startAccessingSecurityScopedResource() returns false for dropped URLs on macOS, unlike fileImporter URLs. Reliable fix is round-tripping each URL through bookmarkData(options:[.withSecurityScope]) and resolving it back (Apple Forums thread/749333). This directly contradicts the doc's claim (04 §7.3) that 'drag-and-drop into the list and onto the dock icon both resolve to security-scoped URLs'.
- REAL limitation #2 (dock-drop / open-with): onOpenURL and NSApplicationDelegate application(_:open:) are reported NOT to fire on the first dock drop, and Universal Links require onContinueUserActivity(NSUserActivityTypeBrowsingWeb) on macOS (not onOpenURL), which can spawn duplicate windows (Apple Forums 769600, 673822; Hacking with Swift forum 24714). Custom URL schemes do trigger onOpenURL. So an NSApplicationDelegateAdaptor is commonly used for robustness — but note onOpenURL CAN work, so the doc's 'requires NSApplicationDelegate' framing (04 §7.3) is an overstatement of necessity even as it correctly flags the area as fragile.
- REAL limitation #3 (list scale): SwiftUI List/Table has macOS-specific performance cliffs at thousands of rows — extracting the row into a subview causes eager full iteration / beachballs at ~5,000 rows, filed FB15645433 and unresolved as of macOS 15.4, March 2025 (Apple Forums 767585). ModernPAR's stated scale is up to 32,768 files (01 §6, par2 limit). So 'sufficient' at that scale is not guaranteed; the doc's own NSTableView/NSViewRepresentable 'escape hatch' (04 §11 risk 4) is a latent AppKit bridge.
- NSDocument: the doc deliberately avoids DocumentGroup/NSDocument (04 §2) and hand-rolls recents — this is a design choice, not a SwiftUI deficiency, so NSDocument bridging is genuinely NOT required; but 'Open Recent' must be built manually rather than inherited from NSDocumentController.
- Drag-INTO-the-list: dropDestination(for: URL.self) exists and URL is Transferable out of the box, but multiple real-world macOS guides still implement file drops via DropDelegate + NSItemProvider (loadItem/public.file-url) due to threading/animation/reliability friction (eclecticlight 2024-05-21; hboon.com), and NSItemProvider is itself an AppKit/Foundation-era API surfaced through SwiftUI.

**Recommendation:** Soften the claim from 'little/no AppKit bridging' to 'SwiftUI-first with a small, well-defined set of bridges.' Specifically: (1) Keep the WindowGroup(for: SessionRoute)/openWindow design, Settings scene, commands/CommandGroup, Table-based file list, .toolbar, and UserNotifications as pure SwiftUI — these are solid. (2) Correct 04 §7.1: drop the NSOpenPanel-for-folders rationale; fileImporter(allowedContentTypes:[.folder]) selects folders on macOS without AppKit. Keep NSOpenPanel only if a specific powerbox pre-selection behavior is needed. (3) Fix 04 §7.3 hard: do NOT assume dropDestination URLs are security-scoped — immediately convert dropped/dock-dropped URLs to security-scoped bookmark Data and resolve back before any engine I/O (matches the round-trip Quinn/DTS endorses); this is also exactly what option (b)/(c) engines need anyway. (4) Plan on an NSApplicationDelegateAdaptor for dock-drop/open-with robustness and test the built app outside Xcode, but know onOpenURL is the primary path; for any URL-scheme entry use schemes (not universal links). (5) Treat the 32k-row file list as a real risk: prototype SwiftUI Table at full scale early with event coalescing and equatable rows, and budget for an NSViewRepresentable(NSTableView) fallback if it can't hold 60fps. Net: the architecture is viable and SwiftUI-first, but the README/marketing-level phrase 'little/no AppKit bridging' is inaccurate — file-access plumbing (bookmarks), dock-drop delegate, and the large-list escape hatch are concrete bridge points to design in.

## Claim 4 — verdict: **nuanced**

**Claim:** Swift/C++ interop in Swift 6.3 / Xcode 26 can compile a non-trivial C++ codebase like par2cmdline-turbo into an SPM target and call it from Swift (ModernPAR doc option a), OR this is impractical and a bundled helper-process/XPC approach is the realistic path (options b/c). Verify the current state of SPM C++ interop and the practical recommendation in docs/research/04-swift-architecture.md.

**Evidence:**
- SPM C++ interop is real and works the way the doc describes. Swift.org 'Setting Up Mixed-Language Swift and C++ Projects' (https://www.swift.org/documentation/cxx-interop/project-build-setup/): 'The interoperabilityMode Swift build setting is used to enable C++ interoperability for a target' (example .interoperabilityMode(.Cxx)), and SPM 'can generate a module map file automatically for a C++ target that contains an umbrella header.' This validates the doc's Package.swift excerpt (Par2Cxx C++ target + PAR2Engine Swift target with .interoperabilityMode(.Cxx)).
- Interop propagation is confirmed verbatim and is a DEPENDENT-direction constraint, exactly as the doc warns. Swift.org project-build-setup: 'Enabling C++ interoperability for a Swift Package Manager target will need other targets that depend on such target to enable C++ interoperability as well.' Swift GitHub issue #66156 (referenced in the doc) is OPEN as of verification: it tracks needing 'internal imports' + cross-platform resilience so a Swift module can hide C++ deps from downstream consumers — i.e. the doc's mitigation (keep PAR2Engine's public surface pure Sendable Swift) does NOT today exempt dependents; they must still enable interop. The doc's architectural rule that ModernPARCore/UI 'must not import the C++ module' is correct but does not eliminate the propagation flag requirement on dependents.
- C++ exceptions cannot be caught by Swift — the doc's single most load-bearing mitigation (the shim must catch exceptions internally) is mandatory, not optional. Swift.org 'Supported Features and Constraints' (https://www.swift.org/documentation/cxx-interop/status/): 'Swift does not support catching C++ exceptions' and 'The running program terminates with a fatal error when a C++ exception that's not caught by C++ code reaches Swift code.' par2cmdline-turbo's libpar2 throws on error paths, so a C-style shim that catches and translates to error codes is required for correctness, exactly as §3 option (a) and §10 state.
- STL boundary support matches the doc's caution. Swift.org status: std::string/std::u16string/std::u32string and specializations of std::vector ARE bridged (as C++ types, not auto-converted to Swift String/Array); but 'Other standard library types, like std::function and std::variant, are not yet supported in Swift'; 'Class and structure templates are not directly available in Swift' (only instantiated specializations via type alias). This supports the doc's 'expose only C-friendly types (POD structs, const char*, function pointers)' shim design.
- par2cmdline-turbo is genuinely a non-trivial C++11 codebase and is embeddable, as the doc claims. GitHub animetosho/par2cmdline-turbo: ~53% C++ / ~38% C, requires C++11, 'removes par2cmdline's OpenMP dependency, replacing it with C++11's threads' (std::thread), GPL-2.0, autotools build (configure.ac/Makefile.am). The src/ directory confirmed to contain the full libpar2 API: libpar2.h/.cpp, par2creator.h/.cpp, par2repairer.h/.cpp, par2cmdline.cpp, reedsolomon/galois/md5/crc + packet classes — so it is usable both as an embeddable library and a CLI, validating the doc's 'critical, verified fact for architecture.'
- Version numbers check out. Swift 6.3 released 2026-03-24 (https://www.swift.org/blog/swift-6.3-released/); the doc's locally-verified Swift 6.3.2 / Xcode 26.5 is consistent and plausible for 2026-06-09. Notably, the Swift 6.3 release notes highlight C interop (new @c attribute) but contain NO C++ interop headline improvements — i.e. C++ interop was not a 6.3 focus, tempering any claim that 6.3 specifically made this easier.
- Real-world SPM friction is significant and lands exactly on par2cmdline-turbo's profile, supporting the doc's risk register rather than the rosy 'first-class' framing. Swift Forums 'Drawbacks/problems with C/C++ interoperability & SwiftPM' (forums.swift.org/t/.../75404): SPM compiles headers as C by default (breaks mixed C/C++ headers like LevelDB), .target(exclude:) does NOT work for headers, and the propagation requirement 'freaks me out' / risks a 'github page full of issues complaining about compilation errors.' Vendoring turbo (mixed C/C++ src, autotools -> hand-written config.h for arm64) hits precisely these pain points. A positive counter-example (Artur Gruchala, arturgruchala.com) shows it working for a self-authored C++ core compiled as an SPM target.
- The doc slightly overstates official framing: it calls interop 'first-class,' but Swift.org 'Mixing Swift and C++' describes it as 'a new feature in Swift 5.9' that is 'actively evolving' and 'currently supports interoperation between a subset of language features.' It does affirm 'A great variety of C++ APIs can be called directly from Swift' and 'Swift uses C++ types and calls C++ functions directly, without any kind of indirection or wrapping' — so direct calling is real, but 'first-class' is the doc's characterization, not Apple's.
- The bundled CLI helper fallback (option b) is independently proven viable: the doc's own local check shows /opt/homebrew/bin/par2 is arm64 v1.1.1; Foundation.Process + async stdout-line parsing is a standard, well-supported pattern; and a CLI over a process boundary is the stronger GPL-2.0 'separate program' license firewall (relevant since embedding GPL C++ makes the whole binary GPL, App-Store-incompatible).

**Recommendation:** Treat the claim as essentially CORRECT but keep it framed as the doc already does — a hedged primary+fallback, not a settled win. Both halves of the OR are true: (a) embedding par2cmdline-turbo as a C++ SPM target and calling it from Swift is technically achievable in Swift 6.3/Xcode 26, AND (b) a bundled CLI helper is a legitimate, lower-risk path. Do NOT promote option (a) to 'first-class/low-risk' in the doc; downgrade the wording from 'first-class C++ interoperability' to 'actively-evolving, subset-based interop' to match Swift.org. Concretely for ModernPAR: (1) Keep the C-style shim non-negotiable — it is REQUIRED, not just advisable, because Swift cannot catch C++ exceptions and libpar2 throws; the shim must catch all exceptions and return error codes, and expose only POD/const char*/function-pointer types (no std::string/std::function/templates across the line). (2) Accept that .interoperabilityMode(.Cxx) propagation cannot be hidden from dependents today (issue #66156 still open) — the mitigation is to keep PAR2Engine the only target that links Par2Cxx and have ModernPARCore/UI depend only on its pure-Swift API, which limits but does not remove the propagation flag. (3) De-risk the autotools/mixed-C-C++-header vendoring early: it is the most likely concrete failure point (SPM treats headers as C by default; exclude: doesn't cover headers) — build a spike that vendors turbo's src/ with a hand-written arm64 config.h and a clean umbrella header before committing to option (a). (4) Genuinely build option (b) HelperProcessEngine behind the same PAR2Engine protocol as a designed-in fallback (the doc's plan), since it is the stronger GPL license firewall and de-risks interop friction. (5) Keep skipping XPC (option c) for v1 as the doc recommends.
